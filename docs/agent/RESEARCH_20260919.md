# 面向教育内容生成的 Agent Harness：研究与选型记录

记录日、资料访问日：**2026-09-19**（Asia/Shanghai）。目标：把较大的出题请求拆成可检查的小任务，用工具校验可计算的答案，并为后续语音、图片、视频工具保留接口。

本记录属于**文献及源码结构调查、架构建议**，不是集成测试报告。本轮没有安装或运行第三方仓库，没有调用生成 API，没有测得本项目的质量、速度或成本收益。以下“建议”均是对本项目的设计推断，不代表原作者已经在中英文计算机本科出题场景验证。

## 1. 结论与选择

**DeepSeek Harness 确实是 DeepSeek 官方项目，不是仅仅同名的第三方项目。** 官方网站直接指向 `deepseek-ai/deepseek-harness`，仓库作者和官网信息互相印证。它目前明确标为 developer preview，不能把“官方”理解为接口稳定或已通过本项目的生产验证。[官方介绍](https://deepseek.com/harness/en/)、[官方仓库](https://github.com/deepseek-ai/deepseek-harness)

对现有 Python / FastAPI / SQLite 应用，建议首版先实现**有明确边界的领域 Agent**：保留现有模型供应商、账号权限、任务队列与数据层，让模型在少量有类型约束的教学工具之间选择，并根据工具反馈决定是否修题。大任务的数量、目标难度、调用预算和最终保存由程序控制。先验证拆分、校验和局部修复的收益，再决定是否引入完整编排框架。

若后续断点恢复、分支、并行题目与人工复核显著增加，可考虑 **LangGraph 的 Python 编排与持久化能力**。DeepSeek Harness 适合作为可替换工具、会话日志、作用域和执行边界的参考，也可以在隔离实验中经官方 Python SDK 接入；首版不建议直接把整套通用 coding harness 嵌入 Web 请求链路。

这里不是“Python 能用 LangGraph，不能用 DeepSeek Harness”：**DeepSeek Harness 已有官方 Python SDK**。真正差别是前者提供 Python 编排，后者的 Python SDK 通过子进程驱动独立的 dsh 运行时，仍需处理跨进程生命周期、工具配置、日志与账号隔离。[Python SDK](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/python/sdk/README.md)

### 2.1 源码结构与值得借鉴的模式

官方架构将会话、提示组装、工具注册、Agent 接口和实际执行循环拆开；Cordis 负责插件与服务组合。以下是阅读源码目录和架构文档后的定位，不是完整代码审计。[架构文档](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/architecture.md)、[packages 目录](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages)

| 源码位置 | 职责 | 教育系统可以借鉴的边界 |
| --- | --- | --- |
| `packages/core/session` | 会话事件 | 原始生成、工具结果、修订记录可追溯 |
| `packages/core/system-prompt` | 提示与工具描述组装 | 按工具能力和任务类型构造上下文 |
| `packages/core/tools` | 有作用域的工具注册与执行 | 只暴露当前任务允许的教学工具 |
| `packages/core/agent` / `agent-loop` | Agent 接口与循环实现分离 | 更换编排方式时保持领域工具稳定 |
| `packages/core/scope` | 注册项的作用域 | 生命周期与资源清理明确化 |
| `packages/sdk/*` / `python/sdk` | 协议与客户端 | Web 后端和外部运行时可独立演进 |

官方架构区分持久会话事件与进程内事件；模型上下文可以由日志投影生成。**日志存在不意味着外部副作用恰好执行一次**，且提交前发生硬中断时并非所有尝试都有完整持久记录。我们的 API 调用及保存操作仍要自行定义重试、去重与不确定结果的处理。

工具执行管线另有独立的前置策略、不可被后续放宽的 guard、执行包装、结果处理和最终结果观察点。这适合借鉴为“先校验账号/参数/预算，再执行，最后统一记录结果”的边界。[工具执行管线](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/tool-execution-pipeline.md)

### 2.2 官方 Python SDK 降低了什么成本，又留下什么成本

SDK 安装同版本的平台运行时 wheel，并通过 `dsh --profile sdk` 启动；**正常运行 SDK 不要求系统另装 Node.js**。运行时包内包含可执行文件及其依赖，因而也不是纯 Python 库。源码开发和外部插件管理是另一个环境问题。[SDK README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/python/sdk/README.md)、[runtime 包说明](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/python/sdk-runtime/README.md)

必须注意的当前接口约束：

- SDK 要求明确的 `dsh_home`。普通轮次除非显式设置 `request_timeout_seconds`，没有默认总时限；`max_tokens` 只是单次模型输出约束，不能替代总调用预算。
- 协议当前没有取消/关闭某个 session 的方法；放弃运行涉及关闭 runtime。协议也没有版本协商的兼容承诺。
- 底层通知覆盖运行时中的 session，应用仍需做作用域过滤与访问控制。官方高级 `Session.run()` 对返回事件和后代通知有自己的筛选语义，不能和底层协议混为一谈。
- `session/prompt` 返回的是持久入队凭证，不等于生成任务成功；完成状态还需要后续事件确认。

前两项 SDK 配置见 [SDK README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/python/sdk/README.md)；协议限制与消息语义见 [protocol README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/sdk/protocol/README.md)，请求类型另核对了 [types.ts](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/sdk/protocol/src/types.ts)。

**本项目的适配推断：** 若试用 dsh，应固定 SDK/runtime 版本，使用隔离的 home 与工作区，经受控领域接口取材料和写结果，不直接授予课程数据库和供应商密钥的任意读取能力。至少验证超时、取消、重启、日志关联和跨账号访问。预置 minimal 是通用执行环境，不应仅凭名称当作我们的最小权限教学工具集。示例中的模型名称也不能直接覆盖本项目已配置的 `deepseek-flash`。

## 3. LangGraph：适用于 Python 的可恢复执行参考

本次旧 `durable-execution` 网页入口跳转到 persistence，正文提取不完整，因此依据**官方 `langchain-ai/docs` 仓库当前的 checkpointers 和 functional-api 文档**核实，不拿第三方镜像当官方。文档未显示单一发表日期，记为持续更新资料，访问日 2026-09-19。

| 已核实行为 | 对本项目的设计含义 |
| --- | --- |
| `checkpointer` 按 `thread_id` 保存状态；完整 checkpoint 位于 super-step 边界 | 一次生成请求应有稳定且由服务端控制的执行 ID |
| 并行节点的已完成写入可用于恢复，恢复不必重跑该批所有节点 | 多题并行时可以保留已通过的题目 |
| `sync` 在下一步前持久化；`async` 边运行边持久化；`exit` 主要在退出时保存 | 对需要可靠恢复的阶段明确选策略，而非假设默认配置足够 |
| 恢复会从入口/检查点边界重放，已记录任务结果可复用 | 不是从原 Python 行号无缝继续 |
| 已开始但未成功完成的 task 可能重跑 | API/写入仍需幂等键或结果核对 |

依据：[官方 Checkpointers](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/checkpointers.mdx)、[官方 Functional API：determinism/idempotency](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx)。阅读深度：相关概念、持久化模式与重放章节；没有穷尽整个框架实现。

SQLite 扩展有同步与 `aiosqlite` 异步实现，官方定位覆盖本地开发、测试及轻量部署。可以与当前技术栈配合，但引入 checkpointer 不会自动继承本应用的账号隔离、任务锁、额度或证据保留规则。共享数据库并发写入、序列化类型与重启测试仍是集成工作。[官方 SQLite Checkpoint README](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-sqlite/README.md)

**采用门槛建议：** 若只需“规划→逐题生成→检查→最多一次修复”，小型持久状态机容易理解；当分支、并行、恢复和人工中断成为主要维护负担时，用 LangGraph 替换编排层的收益更明确。这个门槛是项目判断，不是框架性能结论。

## 5. 与现有 FastAPI + SQLite 应用的衔接

2026-09-19 只读检查了 `app/pipeline.py`、`app/store.py` 的相关实现：

- `Pipeline` 使用 `asyncio.Queue` 与 worker；进入执行时原子地将 queued 改为 running，并复查任务归属。
- 启动时将遗留 running 工作标为失败，再载入 queued；当前行为**不是逐步骤断点续跑**。
- `Store.job` 使用事务和 owner 相关 request key 去重；存在 `job_evidence` 与供应商调用记录的基础。

现有请求去重是可复用基础，但只防止重复创建同一个 job，不能单独解决某次远程 API 已执行而本地尚未落盘的问题。后续实现应保留原归属检查和数据隔离，在工具层再次按 owner/course/job 验证访问权限。

### 5.1 建议的第一版执行流程（项目提案，尚未实现）

1. **冻结需求与槽位**：程序按用户选择确定题数、题型、语言和各难度数量；模型只填充各槽位的学习目标、概念和可验证属性，不能自行改变总配额。
2. **检索并保存证据引用**：使用现有账号过滤后的材料；记录材料/片段标识、版本或哈希，使修订可追溯。
3. **按题生成**：每次输出一题或可控小批，单题采用专门 schema；教学讲解与题目分开生成，最终由组装器形成完整资产，避免每个子任务都被迫返回整份资产。
4. **确定性检查**：检查结构、答案引用、数值/离散结构等可计算属性；工具必须说明自己实际检查了哪个属性。
5. **教学检查**：评审答案解释、证据一致性、题目是否可解、预计难度。难度估计和答案校验分开；模型可明确返回不确定。
6. **局部修复**：依据失败属性只修该题，重新执行相关检查；每题最多一到两轮，达到全局预算就停止并保留失败原因。
7. **整体组装与交付检查**：确认题数、目标分布、重复情况和完整内容结构；未达成要求不伪装成已全部通过。

固定顺序执行上述阶段可以称 workflow；只有模型会基于观察结果选择下一工具、补充检索或不同修复行动，才需要强调 Agent 的自适应部分。两者可以共存，最终终止权和限额由程序掌握。

### 5.2 首批工具应小而可验证

| 工具候选 | 输入与验证对象 | 局限 |
| --- | --- | --- |
| `retrieve_evidence` | 服务端注入账号上下文，按当前课程查询材料 | 返回片段不证明题目所有结论正确 |
| `calculate_expression` | 限定语法的算术/符号表达式和精度 | 不能使用任意 `eval`；工具不负责判断题目假设是否合理 |
| `simulate_algorithm` | 有明确 schema 的图、序列、进程参数及算法名 | 只支持已实现且经测试的算法；未知算法返回 unsupported |
| `check_sql_result` | 独立小型 fixture 数据库、只读查询、显式方言 | SQLite 成功不证明其他数据库方言正确；不得连用户业务数据库 |
| `validate_question` | 单题 schema、选项、答案和局部约束 | 结构正确不等于语义正确 |
| `review_difficulty` | 去掉目标标签的题目、学生背景、统一 rubric | 属于模型代理判断，仍需人工/学生数据校准 |

工具结果建议统一为 `pass / fail / unsupported / error`，附检查属性、输入摘要/哈希、输出、工具版本和证据。**unsupported 与未执行绝不算通过**。通过一个算术检查只能标注对应计算已验证，不能标注整题或难度“已证明正确”。任意代码执行、通用 shell 和无限联网不必进入首版；若后续确需执行生成代码，应有独立执行环境、资源上限和受控输入。

运行中的难度估计可以隐藏目标等级，随后程序比较预期与估计；修复器接收差异。最终论文评审必须另外冻结，不能把被反复用于改写的内部打分直接当作独立效果证据。

### 5.3 状态、预算和证据

建议持久化：run/step/question ID、状态、attempt、输入/输出引用、工具及提示版本、来源快照、调用耗时与费用、错误类型。保留原始输出和后续修订，不用新结果覆盖旧实验。无需为了审计而要求模型输出完整私有思维过程；可保存任务计划、简短决策说明和实际工具轨迹。

每次操作区分 `planned → started → succeeded/failed/unknown`。确定完成的步骤可复用；外部调用开始后失联要记录 unknown，并依据供应商幂等能力或结果查询决定重试。即使使用 LangGraph/dsh，这仍是应用层责任。

调用上限、总时间、每题修复轮数和并发数应独立配置；内部验证与最终实验评审分开记账。持久记录写入要有事务和并发控制，保留用户取消语义。多模态未来作为同一工具接口下的异步任务，需独立产物 schema、状态和预算，不能因为底层提供 API 就自动认为内容已验证。

## 6. 三条实施路径的取舍

## 7. 后续实验建议

先注册四个变体，避免同时改所有环节而无法解释收益：

- **A：现有整体生成基线**。
- **B：分解生成 + 完整组装检查**，无工具答案验证，衡量拆分本身。
- **C：B + 确定性工具验证**，暂不反馈改写，测量发现错误的覆盖率和准确性。
- **D：C + 有界局部修复**，最多一轮起步，测量最终质量与额外费用。

使用同一批冻结任务、材料和目标，主题×语言×难度交叉平衡，保留失败任务作为分母。最终独立评审在看不到方法名、目标标签和中间自评分的输入上进行；若同一评审者参与设计或见过旧结果，要继续披露这一局限。开发集与最终保留测试集分开。

至少报告：完整交付率、格式成功率、答案正确率、工具覆盖率、工具错误接受/拒绝、难度一致率与混淆矩阵、严格达标率、每题及每次任务的调用数/费用/延迟。按成本和时延看质量权衡；增加调用取得的提升不能全归因于架构。可另做相近调用预算的基线对照。

难度匹配仍是教师/模型 rubric 的代理指标；后续学生作答正确率、耗时或 IRT 校准才会提供真实学习者难度证据。任何已有 coding harness 报告的收益，都不能替代这里的测量。
