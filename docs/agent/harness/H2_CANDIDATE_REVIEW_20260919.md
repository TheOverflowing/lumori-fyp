# H2 全候选事后质量复核

日期：2026-09-19。范围：`docs/agent/harness-experiments/H2_20260919`，**3 个实时出题需求、4 个生成候选尝试、2 个注入 canary，全部纳入**。原始实验文件与评分未改写；本复核新增模型 API 调用为 0。

本记录是 **Codex 事后 AI 评审，不是人类金标，也不是完全独立盲评**。当前会话参与了系统实现，读过既有实验结果，并在本次复核中看到了作者答案及系统判定。0/50/100 量表是本次补充诊断，不替代 H2 已冻结指标；难度判断相对于既定本科生背景和项目 rubric，不能等同于学生实测难度。

## 评分口径与覆盖

- 正确性：100＝未发现实质答案、解释或条件错误；50＝主要部分正确，但仍有必须修订的事实、解释、条件或覆盖缺陷；0＝核心答案错误或题目不可成立。
- 难度匹配：100＝清楚符合目标；50＝处于边界，或支架、比较条件使难度目标不清；0＝明显属于其他档位。
- 技术故障没有留下可评题目时记 N/A，并留在请求/交付分母。本轮英文题虽最终协议失败，已经存在完整候选，**不能记 N/A**。

|---|---:|---|---:|---:|

## CPU 英文 hard：数值正确，解释和评价条件有缺陷

作者输入为 A(0,6)、B(1,4)、C(2,2)。RR 使用 q=3、切换开销 1，明确允许提前完成后的下一次切换免费；STCF 开销 0。

| 指标 | RR3 | STCF |
|---|---:|---:|
| 平均响应 | 3 | 0 |
| 平均周转 | 35/3 | 20/3 |
| 切换开销 | 3 | 0 |
| 最后完成 | 15 | 12 |

这些数值与独立手工重建一致。问题在于：

1. t=10 的免费交接是 **C→A**，原因是 C 提前完成，不是答案反复声称的“同一个进程继续”或“A→A”。图像提示词也重复了错误说明。
2. STCF 在题内两项数值目标和开销上均优于 RR，二者又都满足“不超过 3”的预算。题目却要求指出必然牺牲的指标；答案临时改为没有定义或量化的短期公平性，并说 A 被延迟，但 A 在 STCF 中反而于 12 完成，早于 RR 的 13。
3. 题干直接给出 C 在 10 完成、B 在 14 只运行 1 单位等结果提示，预算又没有筛选力。因此其 hard 设计要求部分退化为照规则计算，事后难度评价为 medium/hard 边界，而非稳健的 hard 命中。

STCF 的文字平局规则与工具规则有差异，但本组输入没有触发剩余时间相等的决策，不能凭这一点宣称本次数值算错。

系统 review 的布尔结论全部赞同，最终却多输出 `tool_requests`，违反严格 Review schema，所以任务以 `protocol_failure` 结束。这是格式问题阻止交付，**不是答案 gate 识别上述事实问题**。

## CPU 中文 hard：正确时间线与错误解释同时被批准

作者输入为 P1(0,6)、P2(1,2)、P3(2,4)。其 RR q=2/开销0 和 STCF/开销0 的时间线、平均值均正确：RR 平均响应 1、平均周转 23/3；STCF 为 1/3、19/3；二者最后完成时刻均为 12。

但是答案第 (3) 问声称 t=3 时 P1 剩余 3，应该先跑 P1，同时又给出 P3 从 3 开始的时间线。实际 P1 只在 0–1 运行过，**剩余 5**；P3 剩余 4，应先运行。review 直接复述并认可了这个矛盾。因此不能将正确表格视为正确解释的证明。

第 (4) 问把 q 从 2 改为 3，同时把单位切换开销从 0 改为 1，却将结果解释为单纯时间片效应。按题面的“切到另一任务计费”规则，本问没有提前完成免切换费的豁免，应使用 `early_finish_free=false`。手工重建为：

```text
P1 0–3 → switch 3–4 → P2 4–6 → switch 6–7 → P3 7–10
→ switch 10–11 → P1 11–14 → switch 14–15 → P3 15–16
```

此时开销为 4、最后完成为 16；与原 q=2/开销0 相比，是 **0→4、12→16**。所有任务在第一个切换前到达，期间没有 CPU 空闲，所以最后完成时刻就是总服务量 12 加切换开销；不能另加一个由就绪队列等待造成的 makespan 延迟项。

若作者本意是保持开销为 1、只比较 q，那么 q=2 是开销5/最后完成17，q=3 是开销4/最后完成16。本组固定输入反而明确改善，不能用泛泛的“需要再算”替代分析。在线工具只检查了 q=2 和 STCF，未覆盖 q=3，却给出全计算已验证。这是条件覆盖和文字解释的漏检。

两套计算加概念比较超过简单记忆，但最后的评价条件含混且混改参数，未形成清楚的困难设计任务；难度匹配记 50。

## 事务中文 medium：两次尝试都保留，第二次出现明确语义错误

两次候选基本采用同一交错：A 未提交写甲=60，B 首次读取；A 再写乙=140并提交，B 再次读取并尝试写乙=0。Read Committed 下的读取 **100→60**、成功提交后结果 **60/0**，以及失败后重试整个事务、不能保证一次成功，这些回答正确。

需要修正的是 Repeatable Read 分支：B 在 T4 建立快照后，A 在 T6 提交了对乙的修改，B 再更新该行会遇到并发更新导致的序列化失败，不能直接提交乙=0。没有成功重试时，A 留下的已提交值为 **甲60、乙140**。普通 SELECT 不加锁，不代表 UPDATE 冲突检测消失。[PostgreSQL 17 官方说明 §13.2.2](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-REPEATABLE-READ)

- **尝试 1**：作者没有直接断言这个不可能的 RR 提交，而是用“后续若基于旧快照决策”的一般性说法回答。但题目要求保持完整交错不变，作者未说明具体写入会失败，导致情境解释不完整。在线 solver 进一步明确编造了 RR 覆盖并提交；这一更强错误属于 solver，不能倒算成作者原话。该尝试只因 solver 判 hard 而被拒，未进入正确性 review。
- **尝试 2**：作者将旧 solver 的错误明确写进标准答案，称 RR 下 B 写乙=0并提交、形成不可串行的已提交结果。review 全部批准。这是已交付草稿的事实错误；“RR 可能发生某些序列化异常”的一般性质，不能证明本题这一具体提交历史成立。

两个版本都要求在给定交错上应用可见性规则、比较固定快照、对照资料检查重试方案，属于合理的 medium 应用/分析题。第一次判 hard、第二次判 medium，没有伴随明显的任务简化；不能据此证明难度优化有效。资料没有给出该场景所需的具体写冲突规则，本身也暴露了参考材料覆盖缺口，而非合理的难度提升手段。整事务重试要求另见 [PostgreSQL 17 §13.5](https://www.postgresql.org/docs/17/mvcc-serialization-failure-handling.html)。

## Canary：难度拒绝不能冒充答案错误检测

两个 canary 的题干完全相同，作者答案分别为注入错误版和纠正版，并非实时作者出题。

| Canary | 事后答案判读 | 实際停止原因 | 答案正确性 gate |
|---|---|---|---|
| bad | RR 把新到 C 插到已等待的 B 前，错误；STCF 部分正确 | solver 判 medium，目标 hard | **未执行，不计检出成功** |
| corrected | 手工重建确认两策略数值正确 | 同上 | **未执行，不能判断其放行能力** |

正确 RR 队列在 t=2 为 B,C,A，平均响应应为 1、平均周转 20/3；错误版写成 2/3、6。纠正版修正了这一点。STCF 平均响应为 0、平均周转为 5。

从事后难度看，两条常规时间线、一个单指标占优的选择以及泛化限制说明，更接近 medium；“所有任务完成”在这个有限、已知工作量案例中没有形成有竞争性的约束。因此 difficulty gate 拒绝有合理解释，但这种 AI 判断不是人类金标。无论难度判断是否接受，**本轮都没有实际检验 answer gate 是否能区分 bad 与 corrected**。
