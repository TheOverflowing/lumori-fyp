# H5S / H5G / H5C 独立审计

日期：2026-09-19。本次只读核对指定的三个实验档案、各自 SQLite 调用账本及已有离线测试报告，新增 API 调用 **0 次**。未读取 H5B，未公开完整 reasoning 或凭据。

## 结论与边界

- **H5S：冻结复核 2/2 交付，但 schema 重评没有被触发。** 两份旧题的四个 solve/review 输出一次就满足 schema。不能据此宣称“自动格式修复在线成功率 100%”。
- **H5G：完整新题生成尝试 0/2 交付。** 两题都停在 author 阶段，最后一次请求的 8192 输出 tokens 全部为 reasoning，`finish_reason=length`、`content=""`。没有可交付的最终规格，也未运行 solve/review。
- **H5C：既有错误题被明确的答案检查拦截。** review 的 `answer_correct=false` 并给出正确的 RR 数值修正；虽然难度也不匹配，但系统仍完成答案检查，这符合 H4a 的检查顺序。

这些是不同目的的小规模开发检查，应分开报告。H5S 的两题是 H4B/H5J/H5T 的重复题；H5C 是既有错误 canary。不能把重复复核算成新增题目样本。

全部请求及 `response_model` 均为 `deepseek-flash`。费用字段全部缺失，无法从这些档案得出美元实际费用；`known_cost_usd=0` 不等于免费。延迟来自当前运行记录，不是隔离负载下的性能基准。

三组合计 18 次调用、243,966 tokens。该合计只用于核账，不能合并计算题目正确率。

共同条件为 high 思考、`json_object`、每次上限 8192 tokens、每角色最多 4 次请求、允许一次有条件的 schema 重评。各组全局调用上限分别为 12、16、6。H5S/H5C 的 author 为注入素材、无作者 API 消耗；H5G 使用真实 author。

| 题目 | 调用 | 总 tokens | API 时间累加 | 角色用时 | 结果 |

| 英文 | 4 | 49,952 | 45.425 秒 | 48.445 秒 | 草稿交付 |
| 中文 | 4 | 48,701 | 48.222 秒 | 51.243 秒 | 草稿交付 |

两题完整编译 asset 哈希与 H5T 一致，`compiled_spec` 全部证据也一致。英文/中文的 solve 和 review 控制器 `prompt_sha256` 分别与 H5T 相同。即相同题目在后续采样中得到合规输出；H5S 与 H5T 之间的结果差异，不能归因于从未执行的重评分支。

完整 asset 哈希：

```

中文 f7592c045eb43cdb17eb083bc1c15edec87f2ec79d6251d8c6c053b8a4ea50e0
```

审计结果：实际 solve/review 最终 JSON 4/4，严格业务 schema 4/4，规格绑定 2/2，模型难度 hard 2/2，完整交付 2/2；任何 `*_schema_repair` 阶段记录均不存在，触发次数为 0。这些冻结候选题的独立数值复核见 [H5J/T 审计](H5_JT_AUDIT_20260919.md)，本次不重复计作新样本。

已有 [H5 schema 离线验收](H5_SCHEMA_FINAL_VERIFICATION_20260919.xml) 确实记录 **52 tests、0 failures、0 errors、0 skipped**。它证明被测试的离线分支行为，不是 52 次真实模型运行，也不是线上成功率。本次 S/G/C 都没有触发 schema 重评，故真实模型上的触发后修复效果仍无观测样本。

## H5G：思考用满输出预算后截断

| 题目 | 实际 author 调用 | 总 tokens | API 时间累加 | 角色用时 | 最后请求 |
| --- | ---: | ---: | ---: | ---: | --- |
| 英文 | 2 | 26,467 | 44.731 秒 | 46.115 秒 | 第 2 次 length |
| 中文 | 4 | 86,727 | 80.559 秒 | 82.100 秒 | 第 4 次 length |

两个末次原始返回均有如下实际字段：

```
finish_reason: length
message keys: role, content, reasoning_content
content: ""
tool_calls: absent
completion_tokens: 8192
completion_tokens_details.reasoning_tokens: 8192
```

其中英文末次输入 10,505 tokens，总计 18,697；中文末次输入 29,536，总计 37,728。此前请求是工具调用，不能冒充最终题目 JSON。中文在第 4 次碰到该问题不等于“因请求次数被拒绝”：实际被拒绝的响应仍来自 HTTP 200，直接原因是 `length`，而非本地 request-limit 返回。

转发层保存原始失败响应，以 `invalid_chat_completion` 拒绝。账本两条请求记 failed，agent 以 `provider_error` 停止，没有发布内容、没有自动重试，也没有进入 schema 重评。未出现编译规格、solve 或 review。

因此这里是“输出预算内没有完成最终答案”的执行失败，不能归类成模型已经给出的数值答案错误，也不是额外字段一类业务 schema 失败。现场证据只证明这两次 author 输出被 reasoning 消耗到上限，不证明所有任务都必须提高 token 上限，亦不能证明 JSON 模式失效。

## H5C：答案错误得到明确拦截

题目是既有错误 canary：A/B/C 到达时刻为 0/1/2，服务量为 6/3/1，RR q=2、无切换开销，片尾新到达者先于刚被抢占者入队；这条规则不允许新到达的 C 越过已经等待的 B。

本次 solve/review 各 2 次请求，最后输出均满足 JSON 与业务 schema。solver 评为 medium、目标为 hard；系统继续进入答案复核。review 的关键结论为：

```
answer_correct: false
explanation_correct: false
tool_inputs_match_question: true
calculations_verified: false
source_supported: true
confidence: high
```

最终 `quality_failed`，同时记录答案/解释错误与 `difficulty_mismatch`，不交付。该样例应统计为错误接受数 0/1、正确拦截数 1/1；题目交付 0/1 是预期结果，不能列为系统可靠性下降。

独立按 FIFO 队列与剩余服务量核对 reviewer 修正：

| 策略 | 执行时间线 | 首次开始 A/B/C | 完成 A/B/C | 平均响应 | 平均周转 |
| --- | --- | --- | --- | ---: | ---: |
| RR | A 0–2，B 2–4，C 4–5，A 5–7，B 7–8，A 8–10 | 0 / 2 / 4 | 10 / 8 / 5 | 1 | 20/3 |
| STCF | A 0–1，B 1–2，C 2–3，B 3–5，A 5–10 | 0 / 1 / 2 | 10 / 5 / 3 | 0 | 5 |

RR 响应时间为 0/1/2，周转为 10/7/3；STCF 响应为 0/0/0，周转为 10/4/1。精确分数重新核算分别得到 1、20/3、0、5，与模型纠正和归档工具结果一致。坏答案给出的 RR 2/3 与 6 不成立。

一次既有错误题的成功拦截不能建立整体错误检出率；还需其他错误类型和独立留出案例。

## 可用于阶段记录的表述

在重复的两道冻结题上，high 思考与 JSON 模式本次均完成复核和交付，但未触发新加入的 schema 重评分支；因此该分支仍只有离线验证。两次真实新题作者尝试都因 reasoning 消耗完 8192 输出 token 而未形成最终规格，提示后续应优化阶段范围与预算分配。既有错误 canary 则被明确的答案审查拒绝，并给出经独立复算成立的纠正值。以上结果分别反映复核可用性、生成完成度与错误拦截，不能合并为一个“准确率提升”数字。
