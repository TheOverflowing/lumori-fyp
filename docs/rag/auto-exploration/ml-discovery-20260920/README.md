## 2. 修复前：目录覆盖缺失与弱关键词误命中

两个用户任务的学习目标相同，材料类型均为 `lesson`，难度为 `medium`，自动探索开启。其目录版本为 `cs-public-sources-20260920-v2`，搜索提供方为 `curated`。

这里的 `curated` 是对一组预先审查的公开资料 URL 进行检索，不是全网搜索引擎。旧目录的 40 个 URL 主要覆盖算法、操作系统、数据库和 Python，缺少机器学习入门资料。因此，即使模型正确识别了机器学习主题，也无法从不存在的目录条目中选出证据。

| 实际用户任务 | 输出语言 | 系统识别的知识缺口 | 搜索调用 | 探索模型调用 | 接受资料 | 最终状态 | 探索耗时 |
|---|---|---|---:|---:|---:|---|---:|
| A | 英文 | 定义与范围、主要学习类型、模型构建流程 | 6 | 2 | 0 | `insufficient_evidence` / `no_candidates` | 5,191 ms |
| B | 中文 | 定义、主要学习类型、从数据到评估的流程 | 6 | 1 | 0 | `insufficient_evidence` / `no_candidates` | 1,572 ms |

模型已为每个缺口生成中英文查询。例如，任务 A 的流程查询为 `machine learning workflow training testing model building process`。这说明在这两次诊断中，主题识别与双语查询生成已经工作，目录缺少相关主题才是首要瓶颈。

任务 A 还暴露了弱关键词误命中：查询中的 `process` 将 OpenStax 的操作系统“Processes and Concurrency”带入候选，随后模型将其判为 `irrelevant`。机器学习的建模流程与操作系统进程并非同一概念。任务 B 的 `seen_urls` 为空。由于旧版本未逐次记录搜索响应，本文只报告已保存的候选轨迹，不声称所有旧查询都返回了严格意义上的零条结果。

## 3. 第一轮改进：主题覆盖、歧义约束与搜索审计

目录更新到 `cs-public-sources-20260920-v3`，加入 Google 机器学习入门及监督学习教程的中英文页面，以及 D2L 英文引言的网页与作者 Markdown 原文。Google 页面覆盖概念和入门流程，D2L 提供更完整的定义、训练要素、学习类型和应用背景。

检索匹配同时增加词边界与上下文约束。`process`、`thread`、`kernel` 等歧义词需要相应学科上下文；不能仅因通用词重合就将操作系统材料判为机器学习候选。词边界也避免将 `process` 与 `processing` 等不同词形无条件等同。主题词、课程背景和语言偏好参与候选排序。

新版本开始记录逐次搜索的查询、语言、提供方、状态、候选数量与候选 URL，以便区分以下情况：

1. 目录中没有对应主题，或匹配未找到候选。
2. 找到了候选，但当前网络环境无法下载。
3. 下载和解析成功，但资料与知识缺口无关。
4. 已经入库相关材料，但最终检索上下文没有保留所需证据。

### 3.1 固定旧查询回放

回放使用修复前已经产生的 12 个查询，不重新让模型生成查询。每个原始任务贡献 6 个查询，分别对应 3 个缺口的中英文表达。

| 指标 | 更新后测量值 | 解释 |
|---|---:|---|
| 固定查询数 | 12 | 来自两次已发生的真实用户任务 |
| 返回至少一个候选的查询数 | 12 / 12 | 只表示此次查询集中的候选可获得性 |
| 每个查询返回的候选数 | 4–6 | 原始数量均保存在 JSON 中 |
| 全部查询累计候选位置数 | 58 | 包含跨查询重复，不是 58 份资料 |
| 去重后的 URL 数 | 6 | D2L HTML 与 Markdown 属于同一教材内容的不同呈现 |
| “Processes and Concurrency”候选出现次数 | 0 | 该固定查询集中的已知操作系统误命中被消除 |

不能将 `12 / 12` 写成“召回率 100%”。本次没有穷尽所有相关文档，也没有独立人工相关性标注；同一主题的 12 个查询不代表计算机课程总体分布。该回放表明目录补齐与匹配约束解决了本例的候选发现问题，尚未证明端到端问题已经解决。

### 3.2 下载环境与源文档大小

通过研究工具可以读取 Google 的四个官方页面，并核实其内容和许可；但是项目自身的抓取路径在后续真实试跑中对这四个 URL 均返回 `fetch_failed`。这两个观察并不矛盾：不同工具使用的网络路径和抓取实现不同。当前证据不足以进一步断言是目标站点封禁、地区网络限制、DNS 或 TLS 的某一具体原因。

D2L 作者发布的 Markdown 原文可由项目成功获取，因此成为本次可实际入库的来源。源码格式包含教材的交叉引用和图片引用，不能把这些标记误当成已解析图片或完整展开的公式、图示内容。

另一个限制是单篇资料允许的切块数量。该 D2L 引言在当前切块配置下产生 94 个候选叶块，超过原有 64 块上限。此轮将自动探索的默认单篇上限调到 100，保留数量上限与原有下载、页数、时间及调用预算。94 是本资料在当前配置下的测量结果，并非所有长文档的通用取值。

## 4. 第一次真实复测：发现资料后，仍丢失了学习类型证据

[after-en-01.json](after-en-01.json) 保留了第一轮改进后的真实失败结果。试跑复用了用户的英文学习目标、输出语言、材料类型、难度与学习者描述，在独立临时课程中从零资料开始。试跑的 `count` 为 1，真实用户任务记录为 3；因此这不是所有请求字段完全相同的严格 A/B 实验。

该次试跑的探索上限为 2 轮、3 篇资料、8 个候选、6 次搜索、8 次探索模型调用和 180 秒。它的预算与用户任务原始配置也有区别，不能直接用两者耗时得出速度提升结论。

| 指标 | 第一次真实复测 |
|---|---:|
| 总耗时 | 48,306 ms |
| 探索阶段耗时 | 48,267 ms |
| 探索轮数 | 2 |
| 本地目录搜索调用 | 6 |
| 探索文本模型调用 | 4 |
| 接受并入库的资料 | 1 |
| 拒绝或不可用的候选 | 5 |
| 入库后的检索候选叶块 | 94 |
| 全局检索保留的叶块 | 5 |
| 上下文预算 / 实际序列化 token 数 | 1,024 / 756 |
| 最终状态 | `insufficient_evidence` |
| 终止原因 | `search_budget` |

5 个拒绝项分别是 Google 四个 URL 的 `source_unavailable` / `fetch_failed`，以及 D2L HTML 页面的模型判定 `insufficient`。后者是该次模型筛选结果，不能推广为“D2L 网页内容本身不足”。被接受的是作者仓库中的英文引言 Markdown；其 SHA-256、来源和证据位置已存入试跑文件。

此次初始需求评估形成 4 个固定缺口：定义、主要学习类型、典型流程和实际应用。资料筛选阶段，D2L 原文为全部 4 个缺口提供了精确匹配的引文。对于“主要学习类型”，保存了三个分散位置的证据：

| 证据位置 | 文本页编号 | 字符区间 `[start, end)` |
|---|---:|---:|
| 学习问题分类与监督学习小节 | 1 | 20,078–20,438 |
| 无监督与自监督学习小节 | 1 | 43,088–43,289 |
| 强化学习小节 | 1 | 50,158–50,384 |

这里的“页 1”是 Markdown 解析形成的逻辑文本页，不是纸质教材的页码。精确位置用于复核引文确实存在于抓取正文；它不等同于人工判断引文足以解释整个知识点。

问题出现在资料入库后的上下文选择：系统仍按整个用户请求做一次全局 top-5 检索，且受 1,024 token 预算约束。定义、工作流程与应用的证据被保留，分类段落却没有完整进入随后用于覆盖评估的上下文。最终评估将定义、流程与应用标记为已覆盖，将学习类型标记为未覆盖。

因此，第一次修复后的失败属于“相关资料已经找到并入库，但关键证据在后续检索与上下文组装时丢失”，不能继续简单表述为“网上没有找到资料”。本次最终返回的证据列表为空，是覆盖门槛未通过后的阻断结果，不代表整个探索过程中没有接受过资料。

该运行还显示，第一轮已用尽 6 次搜索预算。进入下一轮时，分类缺口仍未通过，系统于是以 `search_budget` 停止；它没有无限搜索，也没有忽略缺失证据直接生成。

### 4.1 调用量与成本记录

调用账本共 18 项：6 次本地课程目录查询、4 次文本 API、7 次嵌入 API 和 1 次重排 API。其中远程模型 API 共 12 次；目录查询不能混记为付费远程模型请求。

各提供方返回的 `total_tokens` 累计为 39,963。该数跨文本、嵌入与重排能力相加，只用于保存本次账本，不代表单一计价口径。部分调用返回费用字段，完整货币成本未知。未进行教师审核、学生评测或独立人工语义标注。

## 5. 第二轮改进：保留每个知识缺口的已验证证据

针对上述结果，开发调整集中在上下文构建，而不是继续无限扩充搜索关键词：

1. 将来源筛选阶段保存的精确引文映射回当前有效的入库叶块，围绕固定知识缺口收集证据。
2. 在最终上下文中优先保留各个缺口的支撑片段，再补充一般相关片段，避免全部名额被定义性内容占据。
3. 为自动探索的证据上下文采用独立的 4,096 token、最多 24 个命中片段的边界；并保留账号、课程、资料启用状态及源内容一致性检查。
4. 当已接受来源已经为所有固定缺口提供可定位引文时，提前结束当前候选遍历，先重新评估证据是否足够，避免继续下载无必要来源。
5. 最终充分性判断继续由后续覆盖评估完成；“有精确引文”不自动等于“生成质量达标”。

上述目标是让发现、入库和最终使用之间的证据保持连续。仍需真实复测确认它能否解决本例，并检查更高上下文预算对延迟、调用量和费用的影响。

### 5.1 第二次英文复测：正文节选也会丢失关键段落

[after-en-02.json](after-en-02.json) 的结果仍为 `insufficient_evidence`，原因为 `no_usable_sources`。总耗时 21,424 ms，接受资料数为 0；D2L 的 Markdown 和 HTML 均在当次筛选中被判为 `insufficient`，Google 四个页面仍为 `fetch_failed`。账本共 9 项，其中 6 次本地目录查询、3 次文本 API；提供方报告的 token 总数为 11,658。

为区分模型输出波动和算法输入差异，使用同一份 D2L 原文，以及 EN-01、EN-02 各自冻结的知识缺口，重新执行旧版正文节选算法。两次重建的源文件 SHA-256 均为 `fa8e9a8cbe58a2dcb2e7e8a45b86b05c3b45ee0ba370ea4777fbd8856c045db5`，节选长度均为 22,020 字符。

| 原文定义句 | 存在 | 缺失 | 存在 |
| 原文显式训练步骤引导句 | 存在 | 缺失 | 缺失 |
| 监督学习标题 | 存在 | 存在 | 存在 |
| 无监督与自监督学习标题 | 存在 | 存在 | 存在 |
| 强化学习标题 | 存在 | 存在 | 存在 |
| `Key Components` 标题 | 缺失 | 存在 | 存在 |

这些检查针对具体原文标记，不应将“某句话缺失”进一步等同于“全部训练知识缺失”。但它们证明：同一本教材并未变化，需求描述的小幅变化就会使旧的全局通用词评分选中不同正文块，甚至漏掉定义。这是来源筛选前的上下文构造缺陷，与第 4 节发现的入库后全局 top-5 丢失证据发生在不同阶段。

因此，当时的中间版本对正文节选策略作了调整：保留原文开头约 4,000 字符；针对每个缺口分别进行 BM25 排序，并优先考虑该缺口最相关的三个 Markdown 标题所在块；轮流为各缺口选块，总计最多 11 个约 2,000 字符的块，仍受 24,000 字符总上限约束。该策略意在避免所有篇幅被同一组高频泛词竞争走。对于没有 Markdown 标题的文本，正文块排序仍可工作。**它随后被第 5.3 节的候选全文临时索引流程取代，已经不是当前生产路径；此处保留其实现与失败历史。**

来源筛选提示明确允许“支持至少一个知识缺口”的有用部分资料，不要求每一篇材料独立回答所有需求；后续全局覆盖评估仍负责检查所有固定缺口。最终覆盖评估的文本序列化取消了每个来源单独截为 6,000 字符的额外限制，保留整体 24,000 字符边界，减少已选中的多处证据再次被单篇截断的机会。

三个节选 JSON 保存的是经过选择和拼接的 D2L 原文片段。归属为 Aston Zhang、Zachary C. Lipton、Mu Li、Alexander J. Smola，来自 [D2L 英文引言作者源码](https://raw.githubusercontent.com/d2l-ai/d2l-en/master/chapter_introduction/index.md)，依据 [CC-BY-SA-4.0 许可](https://github.com/d2l-ai/d2l-en/blob/master/LICENSE) 保存；本文明确标注其重建、截取和拼接性质，不把片段排列视为原书原始全文顺序的完整呈现。

### 5.3 进一步重构：候选全文先建临时索引，再按知识缺口选择证据

生产流程升级为 `auto-exploration-v2`，新增候选临时索引组件 `app/exploration_staging.py`。本阶段候选检索策略标记为 `candidate_index_gap_retrieval_v1`，后续第 5.7 节加入邻块扩展后升级为 `candidate_index_gap_retrieval_v2`。目标是让来源筛选模型看到由检索算法选出的实际相关片段，避免先凭一段不稳定的整篇节选决定是否值得入库。

当前实现的顺序为：

1. 抓取、许可核查和解析通过后，为该候选资料的完整叶块集合建立任务私有的 SQLite 临时向量索引。超出当前单篇上限的资料仍拒绝；在上限内最多处理 100 个叶块，不用截掉尾部来伪装为完整索引。
2. 针对最多 6 个知识缺口分别构造检索查询，执行向量与词项混合检索 `hybrid_rrf_v1`。每个缺口取 4 个命中，按缺口轮流合并去重；当前版本还在剩余名额内补充同节相邻块，全部仍最多 24 个叶块。
3. 把这些叶块中的原文组织为最多 48 个有 ID 的片段，每个最多 900 字符，总计最多 24,000 字符；保留每个片段的来源叶块、逻辑页和字符坐标。
4. 来源筛选模型返回 `gap_id` 与 `passage_id`。控制器查表取得原文，再执行原有来源和支持关系校验。模型不再承担逐字复制长引文的任务；不存在的 ID、无效支持关系和与原文不一致的数据仍被拒绝。
5. 筛选通过后，将资料晋升为当前账号、课程的正式可检索资料，并复用临时阶段已计算的文档向量，避免晋升时再次进行相同的文档嵌入。
6. 任务结束、中断或服务启动恢复时清理临时正文和向量载荷，保留必要审计摘要。临时资料不因进入筛选阶段就对其他任务或账号可见。

片段 ID 合同标记为 `controller_passage_ids_v2`。来源筛选与最终覆盖评估均由控制器将 ID 还原为真实文本。此设计提高出处和文本一致性的可检验性，但 ID 本身不是语义正确性的证明；是否真正支持某个知识点仍需独立判断。

最终覆盖评估继续保留第 5 节的按缺口锚点补充上下文机制。候选临时索引解决“资料被筛选前看不到关键内容”，锚点保留解决“正式入库后已选证据又被挤出上下文”，两者作用于不同阶段。

### 5.8 实现快照与自动化验证的边界

### 5.9 ZH-06：独立运行发现代理 DNS 地址表示的兼容问题

[ZH-06](after-zh-06.json) 在独立隔离任务中用时 1,695 ms，探索阶段 1,657 ms，以 `insufficient_evidence` / `no_usable_sources` 结束。账本共 7 项：1 次成功文本 API 和 6 次成功的本地目录查询。初始需求为定义、主要类型及简单例子，没有重新加入欠拟合等扩展专题；搜索找到了相关候选，但六个不同 URL 均在读取正文之前被地址检查拒绝，错误码为 `private_address`。这次失败没有进入嵌入阶段，不能与前两次 `time_budget` 合并为同一原因。存储审计中正式资料、索引叶块与临时索引均为 0。

后续真实网络探针观察到，`raw.githubusercontent.com` 的系统解析同时返回 `198.18.0.72` 和 `::ffff:0:c612:48`。后者是 IPv4-translated 形式，末尾嵌入的 IPv4 地址同样为 `198.18.0.72`。已有逻辑认识代理使用的 IPv4 Fake-IP 范围 `198.18.0.0/15`，但不认识这组配对的 IPv6 表示，因而在启用已有的 TLS DNS-over-HTTPS 公网解析后备路径之前就拒绝了整个地址集合。该探针直接确认的是此域名和当前网络环境，不能凭一份探针把六个域名的实际 DNS 响应都视为逐一核验过。

修复新增的唯一识别范围为：IPv6 地址严格位于 `::ffff:0:0:0/96`，没有 scope ID，且其嵌入 IPv4 严格位于 `198.18.0.0/15`。此识别只在 `auto` 模式下触发现有的 TLS DoH 后备解析，不允许直接连接 Fake-IP。`_public_ip` 校验没有放宽，真正的私有地址、包含私有地址的混合响应、其他转换形式（包括 NAT64）以及 `system` 模式下的 Fake-IP 仍被拒绝。DoH 返回的地址继续经过公网地址校验，后续连接仍固定到校验后的数值地址。新策略标记 `DNS_POLICY_VERSION = public_address_pinning_v2` 已纳入探索配置冻结。

[DNS 与下载探针](dns-translated-probe.json) 经上述路径取得公开地址后，成功下载 83,885 字节的 D2L 作者 Markdown。其 SHA-256 为 `fa8e9a8cbe58a2dcb2e7e8a45b86b05c3b45ee0ba370ea4777fbd8856c045db5`，与前面实验使用的原文相同。该探针没有模型调用，只验证域名解析和公开资料下载恢复；它不验证索引、邻块召回、语义覆盖或生成。

补丁对应的[定向后端测试](validation-dns.txt) 为 215 通过、2 条警告，耗时 7.41 秒；[前端测试](validation-frontend-dns.txt) 为 125 通过、0 失败，耗时约 137.73 ms。它们作为后加补丁的独立记录，不能替代或改写第 5.8 节的原始全套测试日志。DNS 修复后的完整真实生成结果应另行追加，不能从下载探针或测试通过预记成功。
