# 高并发逐题子代理实验协议

研究问题：当一份 quiz 需要 20–40 道题时，逐题工作单元的上限 5、10、20、40 如何影响接口吞吐、任务耗时、调用/Token 成本、未通过题目数量和可交付内容质量？所有结果使用 `deepseek-flash`、同一台机器和隔离 SQLite，不触碰用户课程。接口层与完整出题层分开报告。

1. **接口层**：40 个相同的短 JSON 请求，按 4/5/10/20/40 并发，各重复 2 次，顺序正反交替。计批次总耗时、单请求中位/p95 与错误数。它只衡量短响应吞吐，不推断长文本出题质量。
2. **生产流程首轮**：20 题各并发组使用同一冻结来源、语言、难度、题型与题数。最初保留模型自行规划的运行，用于记录规划可靠性；规划随机失败不能纳入并行出题比较。
3. **冻结规划首轮**：用同一份经过结构校验、助手预制的逐题规划消除随机规划差异。生产调度在首题失败后停止派发新题，所以必须同时报告已尝试题数、已通过题数与各门禁失败原因；不同组首轮交付率不能直接视为独立题目正确率。
4. **冻结规划完整暴露**：研究模式在首题失败后仍继续派发其余题目，直到固定的 20 或 40 个题目都尝试。仍执行原作者→解题→复核门禁，整组只要有一题未通过就不会发布。此模式仅用于同题数下的并发效率与逐题产出比较，线上默认仍在失败时停止新派发。
5. **独立内容核对**：在完整暴露运行里，每组从内部已通过题目中用固定 SHA-256 规则抽取最多 5 题，先打乱并隐藏并发条件，再由 Codex AI 对照冻结的真实课程摘录，逐项判断答案事实正确、引用支持、学生可由可见题干作答、是否满足规划目标；保留 `uncertain`，不把内部模型门禁当外部正确率。它不是教师审核、人工标注或学生学习成效实验，样本也不足以做显著性结论。

课程材料来自本仓库已有的本科操作系统（xv6）、数据库（PostgreSQL）与计算机网络开放摘录，原始 URL、许可证、来源哈希见 `scale_q*_*.json` 的 `source_manifest` 和 `benchmarks/quality_latency_v1/dataset.json`。每组题目相同的仅是**规划要求**，模型实际生成的题目与修复次数并未固定，因此端到端耗时仍是探索性样本。既有用户任务默认不修改；实验请求在临时目录运行并在结束后销毁临时数据库，仅保留精简结果、逐题状态与审核样本。

选型规则：只有当更高并发在相同题数下显示可重复的吞吐提升，且接口错误、逐题门禁通过率、独立样本审核与每通过题目的 Token 成本没有明显恶化时，才考虑提高线上默认值。若样本不足或结论冲突，保持默认 4、把 5–40 留作可配置上限，并明确下一轮需要的重复次数。
